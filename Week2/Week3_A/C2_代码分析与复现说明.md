## 2. 原始 Bug：持锁向无缓冲 channel 阻塞发送

修复前的 `mux.go` 逻辑（从 patch 反推的修复前代码）：

```go
func (m *Mux) distribute(event Event) {
    m.lock.Lock()
    defer m.lock.Unlock()      // 锁持到底，函数返回才放
    for _, w := range m.watchers {
        w.result <- event      // ← 问题在这：result 是无缓冲 channel，裸发送
    }
}

func (mw *muxWatcher) Stop() {
    mw.m.stopWatching(mw.id)   // stopWatching 内部要拿 m.lock
}
```

两个要害叠在一起：

1. **裸发送**：`w.result <- event` 没有 select 保护，接收方不在就一直挂着。Mux 的使用前提是"每个 watcher 都有人在读"，但 k8s 里 watcher 的使用者随时可能放弃读（超时、断连、出错返回），这时这个 watcher 的 channel 就成了没人收的"死信箱"。
2. **持锁发送**：distribute 是拿着 `m.lock` 在发。一旦卡在某个死信箱上，锁也跟着被扣下。

## 3. 死锁链：distribute、channel send、Mutex 三者怎么咬死的

这是本周任务第 2 条，我把三个环节的因果关系单独画出来（时序图）：

```
时间 →
goroutine-1 (distribute) :  拿到 m.lock ──→ 发给A成功 ──→ w.result <- event(B) 【卡死：没人接收】
                                                        │ 且 m.lock 一直没释放
goroutine-2 (Stop)       :                    尝试 stopWatching → m.lock.Lock() 【卡死：等 goroutine-1 的锁】
goroutine-3 (B的使用者)   :  已经放弃读 result（死信箱的成因）
其他任何协程              :  只要碰 Mux（Watch/Stop/distribute）→ 全部排队等锁 → 连锁卡死
```

逐环节拆开：

1. **channel send 为什么会卡**：Go 的无缓冲 channel 发送必须等接收方就绪才返回。B 的使用者不再读，发送方就永远停在 `w.result <- event` 这一行。
2. **为什么锁被扣下**：`defer m.lock.Unlock()` 要等 distribute 函数返回，而函数返回要等 for 循环发完——发不完，锁不放。
3. **Mutex 为什么救不了场反而陪葬**：`Stop()` 想把 B 从 watchers 里删掉来"止损"，但 `stopWatching` 先要拿 `m.lock`——锁正卡在死锁源头手里。想清理的人也死了，任何后来碰 Mux 的协程同样排队等死。

一句话：**channel 的"等人来收"和 Mutex 的"等人放锁"互相依赖，形成循环等待**。这是 message passing（channel）和 shared memory（mutex）两种同步机制混用的特有坑——单看哪种机制都没毛病，组合起来才死。论文把这类归为"混合误用"，Week2 同学B 的分析里已经指出，我这周的复现把这个结论跑实了（见第 6 节 goroutine 栈）。

## 4. 官方修复精读：三处改动，缺一不可

patch `435e0b73` 的全部内容：

**改动① watcher 结构体加两个字段：**

```go
type muxWatcher struct {
    result  chan Event
    stopped chan struct{}   // 新增：停止信号
    stop    sync.Once       // 新增：防重复 Stop
    id      int64
    m       *Mux
}
```

**改动② distribute 的裸发送改成 select 双路：**

```go
select {
case w.result <- event:   // 正常发出去
case <-w.stopped:         // 接收方已 Stop，跳过，不再傻等
}
```

**改动③ Stop 先发停止信号，再去拿锁：**

```go
func (mw *muxWatcher) Stop() {
    mw.stop.Do(func() {
        close(mw.stopped)          // 先 close：解围
        mw.m.stopWatching(mw.id)   // 再拿锁清理
    })
}
```

我最初以为核心就是"加个 select"，细看发现三处是咬合的，少一处都修不好：

- **只改②不改③**：select 两个分支——发送成功、或收到 stopped 信号。没人调 Stop 的话 `stopped` 永远不 close，select 还是卡在原地。所以必须有人负责 `close(stopped)`。
- **只改③不改②**：Stop 把 stopped 关了，但 distribute 还是裸发送，根本不看这个信号，照样卡。
- **改动①的 sync.Once 也不能省**：`close` 一个已关闭的 channel 会 panic。watcher 的 Stop 在真实代码里可能被调用方和 defer 各调一次，Once 保证 close 只发生一次。

修复的思路值得记一笔：**它不是消除"持锁期间发送"这个模式，而是给了发送方一个逃逸出口**——只要使用者按约定调 Stop（哪怕人已经不读了），发送方就能从 select 的 stopped 分支走掉，锁得以释放。也就是说修复依赖"使用者最终会调 Stop"这个前提（详见第 9 节我的困惑 2）。

## 5. 复现程序 v4：在同学B v3 基础上完善了什么

同学B 在 Week2 把这个 bug 改了三版（v1 时序错、v2 Stop 启动太晚、v3 定稿），复现代码已经很扎实，踩坑记录我都继承在文件头注释里。这周的完善集中在三处（`repro_k8s_mux.go`，v4）：

| 改动 | 原因 |
|---|---|
| 两个场景拆开，加 `-version=buggy/fixed` 参数 | v3 一个进程先跑 fixed 再跑 buggy，buggy 结尾的全局死锁会杀掉整个进程，两份输出混在一份日志、退出码永远是 2。本周要求各留 3 轮独立日志，必须拆 |
| 全部关键节点打相对时间戳 | v3 只能看出"卡住了"，看不出"谁先卡、卡了多久"。加时间戳后死锁链时序能直接从日志读出来 |
| distribute 发送前逐 watcher 打日志 | v3 卡住之后就 silent 了，看不出卡在给谁发。v4 能精确看到"卡在给 B 发送"这一步 |

场景设计不变（沿用 v3 验证过的正确时序）：watcher A 正常读，watcher B 注册后放弃读但未被移除；distribute 先启动，50ms 后 Stop 启动。

fatal 打出的 goroutine 栈正好是死锁链的四张"现场照片"，和第 3 节的时序图一一对上：

| goroutine | 栈顶状态 | 对应角色 |
|---|---|---|
| 7 | `chan send` | distribute：卡在给 B 发送，**锁在它手里** |
| 18 | `sync.Mutex.Lock` | Stop(B)：等 distribute 的锁 |
| 1 | `sync.Mutex.Lock` | main 收尾：等同一把锁 |
| 6 | `chan receive` | watcher A：等下一个事件（它没参与死锁，但也被全局检测"连坐"） |

这个栈同时实证了论文 Section 8 的两个结论：

1. 内置 deadlock detector 只抓"**全部** goroutine 都卡死"的全局死锁——我们故意让 main 也去等锁才触发它；如果只是 distribute 一个卡住、其他协程还活着（真实 k8s 服务的常态），detector 完全无感。
2. 它的处理方式是把整个进程杀掉（fatal error），不是修复。

## 7. C2 为什么属于 Blocking，以及它与 C1 的区别（任务第 6 条）

**为什么是 Blocking**：按论文的定义，blocking bug 的特征是 goroutine 永久阻塞、程序既不崩溃也不报错（直到某天被外力发现）。C2 完全符合：distribute 卡死在发送上不返回、锁不释放、Stop 排队等锁——每个协程都在"等一个不会来的事件"。我们日志里那个 fatal 不是 bug 自己暴露的，而是 main 也去等锁后触发了运行时的全局检测——**本质上还是"卡死"**，detector 只是顺手补了刀。

**和 C1（Docker ContainerWait）的区别**，我们组两个 blocking 案例其实是同一类问题的两个严重度等级：

| | C1 Docker | C2 Kubernetes Mux |
|---|---|---|
| 卡死的范围 | **单个**子协程泄漏（发送方卡在 `errC <- err`），父协程和其他协程照常运行 | **死锁链**，最终把整个 Mux 和所有使用者拖死 |
| 表面现象 | 进程完全正常，无声无息漏一个协程，最难察觉 | 全局卡死（我们故意触发 detector 才看见 fatal；真实场景同样可能只是"服务没响应"） |
| 根因 | 纯 message passing：无缓冲 channel + 接收方提前退场 | **混合**：channel 的阻塞发送 + mutex 的持有不释放，两者互锁 |
| 修复 | 加缓冲区 `make(chan error, 1)`，一处改动 | 三处咬合的改动（select + stopped 信号 + Once） |
| 防御思路 | "发送方不依赖接收方在场"（缓冲/超时） | "持锁期间不做可能阻塞的操作"——要么先放锁再发，要么给发送留逃逸口 |

给 Pre 讲的时候这个对照可以当主线：C1 是"一个人卡住没人知道"，C2 是"一群人互相等死"，从 message passing 一路讲到混合误用，正好覆盖论文 blocking bug 的两种主要根因。

## 8. 踩坑与困惑（如实记录）

1. **退出码的小坑**：`go run` 结束时在输出里打印 `exit status 2`，但我在 bash 里用 `$?` 拿到的是 1；编译成 exe 直接跑想验证真实退出码时又没执行成功。最后记录以 `go run` 自己打印的 `exit status 2` 为准（日志文件里都有）。退出码在不同调用方式下的差异我没有深究，不影响复现结论。
2. **`-race` 的坑（两个，都已绕过/记录）**：
   - 第一坑：最初用本机自带的 MinGW 8.1.0（2018 年）跑 `go run -race`，报 `exit status 0xc0000139`（DLL 入口点问题）——老 GCC 和 go1.23 的 race 运行时链不上。换 MinGW-Builds **GCC 14.2.0**（UCRT 版，解压即用，没动系统环境）后解决。
   - 第二坑：race 版 buggy 程序触发全局死锁时，Windows 上的 race 运行时走 failfast 路径终止进程，`fatal error` 栈没来得及写进重定向的日志文件（日志停在"收尾"那行）。非 race 版（第 6.3 节）的完整栈可以作参考，两者死锁行为一致。
   - **race 实测结论**：两个版本全程零 `DATA RACE` 告警（fixed 版干净跑完退出码 0；buggy 版跑到收尾被运行时终止）。这印证了论文把两类 bug 分开对待的必要性——race detector 只管数据竞争，对 blocking bug 完全无感；反之亦然，C3 那种 race 用死锁检测也抓不到。检测器各管一摊，没有万能工具。
3. **map 遍历顺序的观察（后来被新证据补上了）**：distribute 用 `for range m.watchers` 发送，Go 故意随机化遍历顺序。留档的 6 轮恰好都是先发 A 再卡在 B。当时我写"6/6 样本太小，不下顺序有偏的结论，别把日志形态当必然"——结果用户本机实跑的那一轮（`screenshots/01_fixed_正常结束.png`）就是**先遍历到 B**：distribute 0.5ms 卡在给 B 的 select 上，50.6ms Stop 解围跳过，直到 51.4ms 才轮到 A 发送、A 收到事件。同一份程序、不同运行，日志形态确实不同，但结论一致（fixed 正常结束、buggy 死锁）。正好印证了当时没敢下的判断。
4. **一个没完全想透的点（实跑截图给了旁证）**：官方修复后 distribute 依然持锁发送。如果某个 watcher 既没人读、又永远没人调它的 Stop，select 还是会卡住，死锁链理论上还在。上面那张 fixed 截图就是旁证：B 没人读，即使打了补丁，整个分发队列照样被拖住 50ms，A 要等到有人 `Stop()` 才收得到事件；如果永远没人 Stop，A 也就永远收不到。我理解真实 k8s 代码里 watcher 使用者的约定是"不用了就 `defer w.Stop()`"，修复堵的是这个约定下的漏洞，而不是理论上所有情况。**所以严谨说法是：补丁给的是逃逸口，不是消除持锁阻塞本身。** 这个理解对不对，准备小组会上问一下。

## 9. 结论：C2 适不适合作为 Pre 扩展案例

**适合，建议放在 C1 之后作为进阶案例。** 理由：

1. **现象有戏剧性**：buggy 版结尾的 `fatal error: all goroutines are asleep - deadlock!` 现场感很强，fatal 栈就是死锁链的现场照片，讲解时可以直接指着栈讲四环节。
2. **教学价值高于 C1**：C1 只讲"无缓冲 channel 要小心"，C2 能讲出"channel + mutex 混用"这个 Go 特有难点，且修复 patch 三处咬合、小巧精悍，适合带着读。
3. **复现零依赖**：纯标准库，`go run` 一条命令，教室机器就能演示。
4. **成本可控**：需要提前准备的只有一张三协程时序图；buggy 演示会杀进程，Pre 时提前声明"退出码 2 属预期"即可。
